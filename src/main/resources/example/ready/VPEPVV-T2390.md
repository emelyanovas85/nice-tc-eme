## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T2390** представляет собой сложный сценарий оркестрации, который нарушает фундаментальные принципы автоматизации: **атомарность**, **единая ответственность** и **детерминированность**. Он не является самостоятельной проверкой, а лишь последовательно запускает набор вложенных тест-кейсов, каждый из которых также имеет критические недостатки.

Ключевые нарушения, делающие автоматизацию невозможной в текущем виде:
1.  **Нарушение структуры вложенных ТК:** Все вложенные тест-кейсы (VPEPVV-T2691, T2358, T2795, T2694, T2808, T2806) содержат заполненный блок **"Предварительные действия"**, что категорически запрещено для вложенных сценариев. Это создает скрытые зависимости и нарушает изоляцию.
2.  **Отсутствие единой ответственности:** Основной ТК проверяет множество разнородных функциональностей (валидация дат, текстовых полей, числовых полей, работа с формами) в одном прогоне.
3.  **Некорректная работа с данными:** В параметрах вложенных ТК содержатся описания условий и логики проверок ("Контроль при вводе...", "Вводимое значение...") вместо чистых тестовых данных.
4.  **Недостаточная детализация шагов и проверок:** Шаги основного ТК, вызывающие вложенные кейсы, не имеют собственных ожидаемых результатов. Ожидаемые результаты во вложенных ТК часто не указывают тип UI-элемента, что критично для селекторов автотеста.
5.  **Несоответствие статусам:** Основной ТК не имеет требуемых статусов "Утвержден" и "АТ принят", а также не имеет зафиксированного успешного прогона.

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разделить VPEPVV-T2390 на отдельные атомарные тест-кейсы, каждый из которых проверяет валидацию одного конкретного поля или логической группы полей.
2.  **Очистка вложенных ТК:** Во всех вложенных тест-кейсах полностью **очистить блок "Предварительные действия"**. Инструкции по снятию фокуса и другие нюансы перенести непосредственно в шаги тестирования или реализовать на уровне фреймворка/хелперов.
3.  **Рефакторинг данных:** Переименовать параметры в блоках "Входные параметры" вложенных ТК, убрав описания условий (глаголы, слово "Контроль"). Оставить только нейтральные имена (например, `ErrorMessage_InvalidDate`, `MaxPositiveLength`) и чистые значения.
4.  **Детализация проверок:** Исправить все ожидаемые результаты, добавив явное указание типа UI-элемента (например, "Поле ввода", "Модальное окно", "Сообщение об ошибке типа span").
5.  **Устранение избыточности:** Объединить повторяющиеся шаги во вложенных ТК (например, ввод различных недопустимых символов) в один параметризованный шаг с использованием наборов тестовых данных (Data-Driven Testing).
6.  **Смена статусов:** После внесения изменений перевести ТК в статус "Утвержден" и провести успешный прогон для фиксации статуса "АТ принят".

Только после выполнения этих действий тест-кейс (или набор новых тест-кейсов) может быть рассмотрен для автоматизации.
