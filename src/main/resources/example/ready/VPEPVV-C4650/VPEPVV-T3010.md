## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T3010** в текущем виде **не пригоден для автоматизации**. Критическими препятствиями являются:
1.  **Нарушение принципа единой ответственности:** Тест покрывает три различных сценария негативной валидации (ошибка подписи, шифрования, доверенности) в одном прогоне, что усложняет локализацию дефектов.
2.  **Зависимость от ручных действий и ОС:** Наличие инструкций по нажатию клавиши **F5**, взаимодействие с **нативным диалогом выбора файлов** и проверка локальной файловой системы ("Открыть папку загрузки", "Открыть файл") делают тест невозможным для выполнения в автоматическом режиме без полной переписки.
3.  **Недетерминированность и отсутствие типизации:** Ожидаемые результаты содержат вариативные формулировки ("сравнить с маской", где маска не определена), динамические даты без алгоритма парсинга и отсутствуют указания типов UI-элементов (кнопка, поле, модальное окно).
4.  **Проблемы с данными:** В блоке "Наборы тестовых данных" присутствуют действия (вызов других ТК), а не только данные. Поле "Сертификат" не используется в шагах. Отсутствуют эталонные файлы для сравнения.
5.  **Статусная дисциплина:** Тест-кейс не имеет утвержденных статусов ("Утвержден", "АТ принят") и истории успешных прогонов ("Пройден").

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разбить тест-кейс на три независимых атомарных теста, каждый из которых проверяет одну конкретную причину ошибки (4001, 4002 и т.д.).
2.  **Устранение ручных шагов:** Заменить все упоминания "обновить страницу (F5)" на механизмы **явного ожидания (Explicit Wait)**. Исключить взаимодействие с проводником ОС, используя прямую передачу пути к файлу. Заменить шаги по открытию файлов/папок на программную проверку наличия и содержимого файлов в директории загрузок.
3.  **Детализация ожидаемых результатов:** Переписать все ожидаемые результаты, указав **тип UI-элемента** (например, `Button "Отправить"`, `Input "Комментарий"`, `Modal "Ошибка"`). Заменить вариативные тексты ошибок на проверку стабильной части строки или регулярное выражение (маску).
4.  **Работа с данными:** Удалить инструкции выполнения других тест-кейсов из блока "Параметры". Перенести логику выбора сертификата в шаги или предусловия. Добавить недостающие эталонные файлы (.xml) во вложения или изменить логику проверки на проверку API-ответа.
5.  **Статусная модель:** Провести ручное прохождение тест-кейса (или его декомпозированных частей), зафиксировать результат "Пройден" и перевести статусы в "Утвержден" и "АТ принят".
6.  **Устранение аббревиатур:** Расшифровать все используемые аббревиатуры (ДЭФ, МЧД, УКЭП и т.д.) при первом упоминании или в глоссарии теста.
