## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T3102** в текущем виде **не готов к автоматизации** из-за фундаментальных нарушений в структуре шагов, описании ожидаемых результатов и управлении тестовыми данными. Ключевые блоки проблем:

1.  **Недетерминированность и сложность шагов:** Наличие логических ветвлений в шагах и предварительных действиях (например, "можно как выбрать... так и ввести", "в противном случае включить") делает невозможным создание линейного автотеста без внедрения сложной условной логики. Использование динамических дат ("<текущий год>") без явного алгоритма генерации нарушает повторяемость теста.
2.  **Неформализованные ожидаемые результаты:** Ожидаемые результаты сформулированы слишком общо ("показываются только значения, соответствующие условию") и не привязаны к конкретным UI-элементам (тип, локатор, состояние). Это не позволяет написать однозначные ассерты. Отсутствует проверка конкретных данных в таблице после фильтрации.
3.  **Нарушение работы с данными:** Блок тестовых данных содержит инструкции ("<не заполняем>") и динамические вычисления, что недопустимо для статических наборов данных. Тест зависит от предустановленных данных в среде без этапа их подготовки (Setup) и очистки (Teardown), что создает риск ложных падений.
4.  **Нарушение принципа единой ответственности:** Один тест-кейс пытается проверить работу фильтров для 12 различных столбцов через параметризацию, что усложняет локализацию дефектов и поддержку скрипта.

**Рекомендации по устранению:**

1.  **Устранить ветвления:** Переписать шаги, зафиксировав один конкретный способ взаимодействия для каждого действия (например, только ввод текста с клавиатуры, только клик по календарю). Вынести проверку и установку чек-боксов в отдельный подготовительный шаг или вложенный ТК, гарантирующий предусловие.
2.  **Детализировать ожидаемые результаты:** Для каждого шага переформулировать ожидаемый результат, указывая:
    *   Тип элемента (модальное окно, кнопка, поле ввода, грид).
    *   Конкретное состояние (открыто/закрыто, активно/неактивно, содержит текст "Х").
    *   Конкретные данные для проверки в таблице (например, "В первой строке грида в столбце 'Тема' отображается значение '...'").
3.  **Исправить тестовые данные:**
    *   Заменить инструкции "<не заполняем>" на явное указание пустой строки или удалить колонку, если поле не используется.
    *   Заменить динамические даты ("<текущий год>") на конкретные фиксированные значения для тестовой среды или вынести логику генерации в код теста (параметризация на уровне кода, а не таблицы).
    *   Добавить этап подготовки данных (создание тестовых записей через API) и очистки после теста.
4.  **Декомпозиция:** Рассмотреть возможность разделения тест-кейса на несколько атомарных тестов (по типам фильтров или группам столбцов) для соблюдения принципа единой ответственности.
5.  **Статусная модель:** Провести тест-кейс, устранить замечания, проставить статусы "Пройден", "Утвержден", "АТ принят" в соответствии с регламентом. Добавить проверку начального состояния через API/БД.
