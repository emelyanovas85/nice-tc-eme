## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T3141** в текущем виде **не готов к автоматизации** из-за фундаментальных нарушений принципов детерминированности, единой ответственности и работы с данными.
Ключевые блокирующие факторы:
1.  **Нарушение единой ответственности:** Тест пытается покрыть два разных сценария (отправка пустой формы и отправка зашифрованных файлов) в одном прогоне через параметризацию, что недопустимо для стабильных автотестов.
2.  **Недетерминированность:** Использование динамической даты ("<текущая дата>") без явной фиксации в параметрах приводит к невозможности предсказать ожидаемый результат в шагах проверки.
3.  **Логические ветвления и смешение логики с данными:** Наличие условий "выполнить любое из действий" в шагах и перенос логики выполнения (условия пропуска шагов, вызовы других ТК) в колонки тестовых данных делает сценарий нелинейным и сложным для интерпретации фреймворком.
4.  **Взаимодействие с ОС и внешним ПО:** Шаги требуют ручного взаимодействия с проводником Windows и утилитой "КриптоАРМ", что невозможно реализовать в UI-автотесте без выноса в отдельные сервисные методы или мокирования.
5.  **Низкое качество описания шагов:** Ожидаемые результаты не содержат типов UI-элементов, что критично для селекторов. Отсутствуют эталонные файлы для сравнения содержимого.

**Рекомендации по устранению:**
1.  **Разделение сценариев:** Разделить тест-кейс на два независимых:
    *   *TC_1:* Проверка отправки формы без вложений (негативный/позитивный сценарий валидации).
    *   *TC_2:* Проверка отправки формы с зашифрованными вложениями (полный цикл с расшифровкой).
2.  **Параметризация данных:**
    *   Ввести явный параметр `TestDate` в начале теста и использовать его во всех шагах заполнения и проверках вместо "<текущая дата>".
    *   Очистить таблицу тестовых данных от действий, ссылок на другие ТК и условий. Перенести логику вызова вспомогательных ТК (подготовка сертификатов) в блок `Pre-conditions` основного теста или в фикстуры.
3.  **Формализация шагов:**
    *   Убрать все логические ветвления ("если", "или"). Описать строго линейный сценарий для каждого из новых тест-кейсов.
    *   Переписать шаги взаимодействия с файлами: заменить "открыть проводник" на программную загрузку через `input[type=file]`.
    *   Вынести операции с "КриптоАРМ" в отдельные методы утилит (Keywords), вызываемые в шагах теста без описания UI-действий.
4.  **Доработка ожидаемых результатов:**
    *   Для каждого шага явно указать тип проверяемого элемента (Кнопка, Поле, Таблица, Модальное окно).
    *   Добавить в блок "Вложения" все необходимые эталонные файлы (.xml, .txt) для сверки содержимого.
    *   Уточнить проверки статусов: для позитивного теста ожидать только успешный статус.
5.  **Статусная модель:** Перевести тест-кейс в статус "Утвержден" / "АТ принят" после внесения правок.

Только после устранения указанных замечаний и повторной проверки по чек-листу (целевой уровень >70%) тест-кейс может быть взят в работу по автоматизации.
