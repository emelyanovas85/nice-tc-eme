## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T2568** в текущем виде **не готов к автоматизации** (уровень готовности 34%). Критическими проблемами являются:
1.  **Нарушение принципа атомарности и единой ответственности:** Тест охватывает слишком широкий сценарий (от заполнения формы до криптографической расшифровки ответов), что делает его хрупким и сложным в отладке.
2.  **Зависимость от внешних тест-кейсов и ручных действий:** Наличие шагов "Выполнить ТК..." и инструкций для ручного тестирования ("Для РТ", описание GUI КриптоАРМ) делает невозможным прямое исполнение скриптом.
3.  **Недетерминированность и логические ветвления:** Шаги содержат условия ("в случае если...", "выполнить любое из...") и неопределенные ожидания времени, что недопустимо для автотестов.
4.  **Низкое качество описания шагов и ожидаемых результатов:** Отсутствие конкретных имен UI-элементов, типов контролов, привязки проверок к конкретным объектам (строкам таблиц, полям форм). Взаимодействие с нативными диалогами ОС и сторонним ПО описано через GUI, а не через API/CLI.
5.  **Проблемы с тестовыми данными:** В колонках данных присутствуют ссылки на другие ТК и описания сценариев вместо чистых данных. Отсутствует согласованность между вложениями и данными.

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разделить тест-кейс на несколько независимых сценариев:
    *   *ТК 1:* Заполнение и отправка формы (до статуса "Отправлено").
    *   *ТК 2:* Проверка смены статусов и истории взаимодействия (через API/UI).
    *   *ТК 3:* Скачивание ответных файлов и валидация их структуры/содержимого (с вынесенной логикой расшифровки в отдельную утилиту/ключевой шаг).
2.  **Устранение зависимостей:** Заменить шаги "Выполнить ТК..." на вызовы API для подготовки тестового окружения или инкапсулировать необходимую логику внутрь новых атомарных тестов.
3.  **Детерминизация:** Удалить все логические ветвления из текста шагов. Реализовать проверку условий (например, наличие модального окна) как отдельные шаги с явными ожидаемыми результатами. Заменить неопределенные ожидания ("~15 минут") на явные ожидания события (polling статуса).
4.  **Доработка шагов и ОР:**
    *   Переписать шаги, убрав инструкции для ручного тестирования.
    *   Заменить взаимодействие с нативными диалогами (проводник, уведомления) на работу с веб-элементами (`input type='file'`) или проверку файловой системы.
    *   Детализировать ожидаемые результаты: указывать тип и имя каждого проверяемого элемента (например, "В таблице 'История' в строке с ID='{ID}' колонка 'Статус' содержит значение 'Принято'").
    *   Вынести конкретные команды криптографии (КриптоАРМ) в конфигурацию или вспомогательные скрипты, оставив в ТК только вызов утилиты.
5.  **Очистка данных:** Удалить из колонок тестовых данных ссылки на ТК и описания сценариев. Обеспечить соответствие списка вложений данным, используемым в шагах.
6.  **Актуализация статусов:** Провести ручной прогон теста, установить статусы "Утвержден" и "АТ принят", убедиться в актуальности даты прохождения.
