## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T169** в текущем виде **не пригоден для автоматизации** из-за фундаментальных нарушений принципов тестируемости и автоматизации. Ключевыми проблемами являются:
1.  **Недетерминированность и внешние зависимости:** Наличие CAPTCHA, зависимость от реальной почты и времени её доставки, а также необходимость взаимодействия с нативными диалогами ОС и сторонним ПО (КриптоАРМ) делают тест нестабильным и сложным в поддержке.
2.  **Нарушение атомарности:** Тест покрывает слишком широкий E2E сценарий (восстановление доступа, работа с криптографией, смена пароля, авторизация), что затрудняет локализацию ошибок и увеличивает время выполнения.
3.  **Проблемы с данными и окружением:** Тест требует специфической настройки окружения (установленные сертификаты, ПО), использует некорректные тестовые данные (условия вместо значений) и не обеспечивает изоляцию данных (требует ручной очистки).
4.  **Низкое качество описания шагов:** Шаги содержат логические ветвления, общие формулировки без конкретики, аббревиатуры без расшифровки и нечеткие ожидаемые результаты, что делает невозможным их однозначную интерпретацию скриптом.

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разбить текущий сценарий на несколько независимых атомарных тестов:
    *   Тест UI формы восстановления пароля (без реальной отправки).
    *   Тест логики отправки запроса (с мокированием почты).
    *   Тест процесса расшифровки (как отдельный скрипт или юнит-тест).
    *   Тест смены пароля (с подготовленным токеном).
2.  **Устранение внешних зависимостей:**
    *   Заменить CAPTCHA на тестовый режим или отключить её в тестовом окружении.
    *   Использовать мокирование почтового сервиса или выделенный тестовый ящик с предсказуемым API.
    *   Мокировать взаимодействие с крипто-плагинами и нативными диалогами, либо использовать специализированные инструменты для работы с ОС, вынеся это в отдельный слой абстракции.
3.  **Доработка тестовых данных и шагов:**
    *   Убрать логические ветвления из шагов.
    *   Конкретизировать все шаги: явно указать имена полей, типы элементов и ожидаемые значения.
    *   Расшифровать все аббревиатуры (МЧД, ЛК, КО, КГРКО).
    *   Исправить набор тестовых данных: убрать условия ("<Не добавлять>"), удалить неиспользуемые колонки ("№").
    *   Добавить недостающие вложения и привести типы файлов к регламенту.
4.  **Автоматизация подготовки и очистки:** Реализовать автоматическую подготовку предусловий (создание пользователя, генерация токенов) и пост-условий (удаление данных, сброс пароля) через API, исключив ручное вмешательство.
5.  **Статусная модель:** Привести статус тест-кейса к требуемым значениям ("Утвержден", "АТ принят") и обеспечить прогон теста для фиксации статуса "Пройден".

Только после выполнения данных рекомендаций тест-кейс может быть рассмотрен для автоматизации.
