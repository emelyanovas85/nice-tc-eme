## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T2431** представляет собой сложный сценарий-обертку ("набор тест-кейсов"), который нарушает фундаментальные принципы автоматизации: **атомарность**, **единая ответственность** и **четкость ожиданий**.
Тест не проверяет одну конкретную функцию, а оркестрирует выполнение более 20 вложенных тест-кейсов для проверки множества полей в двух разных разделах формы. Это делает его хрупким, сложным в отладке и поддержке. Кроме того, выявлены критические ошибки в тестовых данных (неверные номера столбцов в сообщениях об ошибках), которые приведут к ложным падениям автотестов. Статус тест-кейса не соответствует требованиям для передачи в автоматизацию.

**Рекомендации по устранению:**

1.  **Декомпозиция (Приоритет 1):** Разделить данный тест-кейс на несколько атомарных тест-кейсов.
    *   Выделить отдельные ТК для проверки каждого поля или логической группы полей (например, "Проверка валидации колонок 2-5 Раздела 1", "Проверка валидации колонок 1-6 Раздела 2").
    *   Убрать прямые вызовы ID других ТК из шагов, если это возможно, или оформить их как корректные, параметризованные под-сценарии с явными ожиданиями в родительском ТК.

2.  **Исправление тестовых данных (Приоритет 1):**
    *   Внимательно проверить и исправить все параметры, содержащие тексты ошибок. Убедиться, что номер столбца в сообщении об ошибке соответствует проверяемому столбцу (сейчас везде копируется "столбец 2").
    *   Удалить неиспользуемые колонки из набора тестовых данных ('Форма', 'Блок 1', 'Блок 2') или начать их реально использовать в шагах через параметризацию.

3.  **Уточнение ожидаемых результатов:**
    *   Во всех шагах явно указывать тип UI-элемента (контейнер, модальное окно, поле ввода) в ожидаемых результатах.
    *   Избегать описания состояния системы ("Форма закрыта") без привязки к исчезновению конкретного элемента.

4.  **Статус и документация:**
    *   Провести ручное прохождение тест-кейса (или его новых атомарных версий), проставить статус "Пройден" и перевести ТК в статус "Утвержден" / "АТ принят".
    *   Добавить проверку начального состояния системы (API/БД запрос) в предварительные действия.

5.  **Оптимизация структуры:**
    *   Вместо дублирования шагов с вызовом одного и того же вложенного ТК для разных колонок, использовать механизм параметризации (Data-Driven Testing), передавая номер колонки и ожидаемую ошибку в один универсальный шаг проверки.
