## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T2834** в текущем виде **не готов к автоматизации** и требует фундаментальной переработки. Критическими проблемами являются:
1.  **Нарушение атомарности и зависимости:** Тест зависит от выполнения других тест-кейсов (VPEPVV-T1082, VPEPVV-T2979) и содержит вызовы внешних ТК в шагах и параметрах.
2.  **Отсутствие единой ответственности:** Тест проверяет слишком широкий спектр функциональности (загрузка, заполнение, валидация, отправка, статусы, верификация архивов) в одном сценарии, что делает его хрупким и сложным для отладки.
3.  **Некорректная работа с данными:** Параметры содержат инструкции по выполнению других ТК, а не чистые данные. Отсутствует механизм автоматической подготовки тестовых данных (подписанные/зашифрованные файлы генерируются вручную).
4.  **Нечеткие ожидаемые результаты:** Ожидаемые результаты не привязаны к конкретным типам UI-элементов, содержат динамические значения времени и описания, требующие ручной интерпретации.
5.  **Взаимодействие с ОС:** Шаги содержат действия с нативными диалогами проводника и файловой системой, что недопустимо для UI-автоматизации.
6.  **Статус тест-кейса:** ТК не имеет требуемых статусов "Утвержден" и "АТ принят", а также не имеет записей о успешном прохождении.

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разделить тест-кейс на несколько атомарных тестов:
    *   ТК на загрузку и валидацию формы.
    *   ТК на прикрепление файлов и проверку UI.
    *   ТК на отправку ЭС и проверку статусной модели.
    *   ТК на верификацию архива ответа (отдельно).
2.  **Инкапсуляция зависимостей:** Заменить вызовы других ТК на API-методы подготовки данных или реализовать логику создания сертификатов/доверенностей внутри предусловий каждого нового атомарного теста.
3.  **Автоматизация данных:** Реализовать скрипт генерации тестовых файлов (.sig, .enc) в рамках CI/CD пайплайна или использовать моки/фикстуры. Убрать из параметров ссылки на ТК и инструкции, оставив только имена файлов или идентификаторы.
4.  **Детализация шагов и проверок:**
    *   Переписать все шаги, убрав условную логику ("В случае...") и альтернативные действия.
    *   Уточнить ожидаемые результаты, указав тип элемента (Кнопка, Поле, Таблица, Сообщение) и конкретное ожидаемое состояние.
    *   Для динамических значений использовать маски, регулярные выражения или извлечение актуальных значений из контекста теста.
5.  **Устранение взаимодействия с ОС:** Заменить шаги работы с проводником и папкой загрузок на программную проверку наличия файлов в директории через код теста или API. Использовать механизмы загрузки файлов через `input[type='file']`.
6.  **Актуализация статусов:** Провести ручное прохождение тест-кейса (или его декомпозированных частей), установить статусы "Утвержден" и "АТ принят", зафиксировать дату прохождения.

Только после выполнения данных рекомендаций тест-кейс (или набор новых тест-кейсов) может быть рассмотрен для автоматизации.
