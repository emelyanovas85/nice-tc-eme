## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T2381** имеет низкую готовность к автоматизации (40%) из-за нарушения фундаментальных принципов написания автотестов: **детерминированности**, **единой ответственности** и **четкости ожидаемых результатов**.
Тест представляет собой сложный сценарий "все-в-одном", который пытается проверить структуру формы, динамику блоков, валидацию, автозаполнение и работу с файлами в рамках одного прогона. Это делает его хрупким и сложным в отладке.

**Ключевые нарушения:**
1.  **Нарушение единой ответственности:** Один ТК проверяет множество независимых аспектов (структура, UI-состояния, валидация, данные).
2.  **Недетерминированность:** Наличие условных конструкций ("При появлении...", "Если...") в предварительных действиях и шагах, а также требование сравнивать списки "без учета порядка" без явной алгоритмизации.
3.  **Нечеткие ожидаемые результаты:** Использование визуальных критериев ("красная рамка") вместо проверки атрибутов/CSS-классов; отсутствие указания типов UI-элементов (кнопка, поле, диалог).
4.  **Проблемы с данными:** Зависимость от данных профиля пользователя без явной параметризации; неиспользование declared параметров в шагах; наличие действий и условий в блоке параметров.
5.  **Статусная модель:** ТК не имеет требуемых статусов "Утвержден" и "АТ принят", а также истории успешных прогонов.

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разбить текущий тест-кейс на несколько атомарных тестов:
    *   ТК 1: Проверка статической структуры формы и атрибутов полей.
    *   ТК 2: Проверка динамики блоков (сворачивание/разворачивание).
    *   ТК 3: Проверка добавления/удаления строк отчета.
    *   ТК 4: Проверка валидации и обязательности полей.
    *   ТК 5: Проверка автозаполнения данными из профиля (с явным созданием тестовых данных).
2.  **Устранение ветвлений:** Переписать предварительные действия и шаги, убрав конструкции "Если/При появлении". Обработку всплывающих окон вынести на уровень тестового фреймворка (хуки, фикстуры).
3.  **Детализация проверок:** Заменить описания визуальных эффектов ("рамка") на проверку конкретных CSS-классов или атрибутов `required`/`invalid`. Для каждого проверяемого элемента явно указывать его тип (Input, Button, Dialog, Accordion).
4.  **Работа с данными:**
    *   Исправить использование параметра `{Форма}` в шагах (заменить хардкод на переменную).
    *   Убрать описания действий и нормативные ссылки из блока параметров.
    *   Добавить эталонный файл для проверки расширений в блок вложений.
5.  **Актуализация статусов:** Провести ручное прохождение тест-кейса, установить статусы "Утвержден" и "АТ принят", зафиксировать дату прохождения.
