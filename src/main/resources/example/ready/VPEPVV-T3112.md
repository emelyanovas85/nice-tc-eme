## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T3112** представляет собой монолитный сценарий ("God Test"), пытающийся проверить всю форму целиком (более 70 шагов), что нарушает фундаментальные принципы автоматизации: **атомарность**, **единая ответственность** и **детерминированность**. Тест не является изолированным, зависит от порядка выполнения шагов внутри себя, не имеет четкой очистки данных (teardown) и содержит множество шагов-заглушек (вызовы других ТК без явных ожидаемых результатов) и служебных заголовков. Кроме того, тест имеет критические логические ошибки (шаг 75) и не соответствует требованиям к статусам выполнения.

**Рекомендации по устранению:**

1.  **Декомпозиция (Разделение):** Разбить данный тест-кейс на множество мелких, атомарных тест-кейсов. Каждый новый ТК должен проверять одну конкретную функциональность:
    *   Отдельные ТК для валидации каждого поля (длина, формат, обязательность).
    *   Отдельные ТК для проверки логики раскрытия/скрытия блоков.
    *   Отдельные ТК для проверки динамического добавления полей.
2.  **Устранение избыточности:**
    *   Удалить шаги, являющиеся заголовками разделов (шаги 5, 17 и аналоги).
    *   Заменить многократные вызовы одних и тех же вложенных ТК на параметризованные шаги или циклы в коде автотеста, если это позволяет фреймворк.
3.  **Детализация шагов и ожидаемых результатов:**
    *   Переформулировать шаги, содержащие разрывы действия, в одно четкое предложение.
    *   Во всех ожидаемых результатах явно указывать **тип UI-элемента** (ComboBox, Input, Label, Container) и конкретное состояние (текст, класс, стиль).
    *   Исправить логическую ошибку в шаге 75 (соотнести действие выбора и ожидаемый результат).
    *   Для шагов, вызывающих другие ТК, явно прописать ожидаемый результат текущего шага.
4.  **Исправление структуры данных:**
    *   Удалить неиспользуемую колонку 'Блок 2' из наборов тестовых данных.
    *   Убрать описания действий из значений параметров тестовых данных.
5.  **Изоляция данных:**
    *   Добавить явные шаги по очистке тестовых данных (удаление созданной формы/черновика) в конце теста (Teardown).
    *   Реализовать проверку начального состояния через API/БД перед началом теста.
6.  **Статусы:**
    *   Привести статус тест-кейса к требуемым значениям ("Утвержден", "АТ принят") и обеспечить успешное прохождение теста для фиксации статуса "Пройден".

Только после выполнения декомпозиции и устранения указанных замечаний тест-кейс (вернее, набор новых тест-кейсов) может быть рассмотрен для автоматизации. В текущем виде автоматизация данного монолита приведет к созданию нестабильного, трудно поддерживаемого и ненадежного автотеста.
