## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **ASLUNOHOD-T67** представляет собой сложный интеграционный сценарий (End-to-End), который нарушает принципы атомарности и детерминированности, критически важные для автоматизации.
Ключевые недостатки:
1.  **Отсутствие параметризации:** Конкретные данные (URL, имена моделей, текст запроса, названия ТК) захардкожены в описании шагов или отсутствуют, вместо того чтобы быть вынесенными в блок "Параметры". Это делает тест негибким и недетерминированным.
2.  **Некорректные ожидаемые результаты:** Ожидаемые результаты описывают действия пользователя ("Указаны поля", "Введен запрос"), а не проверяемое состояние системы (тип элемента, конкретное значение, видимость). Отсутствует проверка заголовков таблиц при проверке данных в них.
3.  **Нарушение атомарности шагов:** Шаги заполнения форм не содержат завершающих действий (нажатие кнопок "Генерировать", "Сохранить"), которые вынесены в отдельные шаги, что усложняет отладку.
4.  **Неполные предусловия:** Отсутствуют указания на роль пользователя, необходимое ПО и проверку начального состояния системы. Статус тест-кейса не соответствует требованиям ("Draft" вместо "Утвержден").

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разбить текущий тест-кейс на несколько более мелких:
    *   ТК на проверку UI окна настройки (открытие, наличие полей).
    *   ТК на проверку логики генерации (с моками или фиксированными данными).
    *   ТК на проверку сохранения и отображения результата в таблице.
2.  **Параметризация:** Вынести все переменные данные (URL, ModelName, AiPrompt, AtcName, AtcType, UserRole) в блок "Параметры" или "Наборы тестовых данных". Использовать синтаксис `{ParameterName}` в шагах.
3.  **Детализация Ожидаемых Результатов:** Переписать все ожидаемые результаты, указывая:
    *   Тип UI-элемента (Поле ввода, Кнопка, Таблица, Модальное окно).
    *   Конкретное ожидаемое значение или состояние (видимость, текст, выбор).
    *   Для таблиц: обязательно добавлять проверку заголовков столбцов вместе с проверкой данных строки.
4.  **Исправление шагов:**
    *   Объединить шаги заполнения форм с шагами нажатия кнопок подтверждения (согласно Исключению 2 из требований).
    *   Убрать шаг открытия приложения, перенеся его в предусловия. Первый шаг должен начинаться с действия внутри открытого приложения.
    *   Расшифровать все аббревиатуры (ИТС, АТК, ТК) при первом использовании или в глоссарии.
5.  **Актуализация метаданных:**
    *   Изменить статус ТК на "Утвержден" или "АТ принят".
    *   Добавить в предусловия роль пользователя и требуемое ПО/права доступа.
    *   Явно указать отсутствие зависимостей от других ТК или добавить ссылки на них.

После выполнения данных рекомендаций уровень готовности тест-кейса к автоматизации значительно повысится.
