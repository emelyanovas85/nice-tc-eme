## 4. Вывод и рекомендации

**Основная проблема:**
Тест-кейс **VPEPVV-T2451** не готов к автоматизации в текущем виде, так как нарушает фундаментальные принципы атомарности и проверяемости.
1.  **Отсутствие атомарности и единой ответственности:** ТК представляет собой монолитный регрессионный сценарий, проверяющий всю форму целиком (более 20 полей и 3 раздела). Это делает тест хрупким: при падении невозможно быстро локализовать дефект.
2.  **Неявные ожидаемые результаты:** Большинство шагов (1-47) делегируют проверку вложенным тест-кейсам через конструкцию "Выполнить тест id=...", не описывая ожидаемый результат в явном виде (UI-элементы, сообщения об ошибках). Для автоматизации каждый шаг должен иметь четкий ассерт.
3.  **Структурные ошибки:** Наличие шагов-заголовков (22, 26), которые не несут функциональной нагрузки, и отсутствие статусов прохождения ("Утвержден", "АТ принят", "Пройден").

**Рекомендации по устранению:**
1.  **Декомпозиция:** Разделить данный тест-кейс на множество мелких атомарных тестов. Создать отдельные ТК для проверки каждого поля или логической группы полей (например, "Валидация поля ИНН", "Проверка лимита символов в поле Наименование").
2.  **Явные ассерты:** В каждом шаге явно прописать ожидаемый результат в терминах UI (тип элемента, текст сообщения, цвет рамки), а не ссылаться на выполнение других тестов.
3.  **Параметризация:** Вместо дублирования шагов с вызовом одних и тех же вложенных тестов с разными данными, использовать механизм Data-Driven Testing (параметризованные наборы данных).
4.  **Очистка структуры:** Удалить шаги, являющиеся просто заголовками разделов.
5.  **Актуализация статусов:** Провести ручное прохождение обновленных тест-кейсов и проставить необходимые статусы ("Утвержден", "АТ принят", "Пройден") с актуальными датами.
6.  **Проверка предусловий:** Добавить в предварительные действия проверку чистоты данных через API/БД перед началом тестирования.
